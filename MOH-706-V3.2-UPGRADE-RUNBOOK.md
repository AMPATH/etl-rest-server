# MOH 706 ETL — v3.1 → v3.4 upgrade runbook

Upgrades `etl.flat_moh_706_report` (family) to **v3.4** of
`generate_flat_moh_706_v1`, delivering the blank-columns release: order
adoption for obs-only rows (F1), deterministic FHIR report pick (F2),
relaxed Path U panel capture + anti-overlap guard (F3), the
`result_creator` column (F6/D11), and the widened `concept_set_map` scope.

> **v3.3 (2026-10-22):** member obs captured under a panel row no longer also
> get standalone register rows (F3b — the v3.2 grain double-counted panel
> analytes in the `*_with_members` indicators).
>
> **v3.4 (2026-10-23):** the dictionary nests panels (panel → sub-panel →
> leaf); member capture now reaches leaf analytes through intermediate
> sub-panels (Path G2) and skips valueless sub-heads, and
> `refresh_concept_set_map` carries transitive leaf edges only. Reinstall
> BOTH `generate_flat_moh_706.sql` and `create_flat_moh_706_results.sql`,
> re-run `CALL etl.refresh_concept_set_map(NULL);`, then a full rebuild —
> required even from a v3.3 build.

**Source files** (etl repo, branch `feat-moh-706-register-fixes`):

- `etl-scripts/stored-procedures/datalake/create_flat_moh_706.sql`
- `etl-scripts/stored-procedures/datalake/create_flat_moh_706_results.sql`
- `etl-scripts/stored-procedures/datalake/generate_flat_moh_706.sql`

Companion retrieval changes (etl-rest-server, patient-list **v1.2**) can be
deployed before or after this upgrade **provided Step 1's ALTER has run** —
v1.2 reads `fbc.result_creator` and fails with `ER_BAD_FIELD_ERROR` until the
column exists. Before the v3.2 build backfills it, the officer column simply
falls back to the FHIR performer (pre-v1.2 behavior).

All statements run on the analytics ETL database (`etl` schema) unless noted.

## 0. Pre-flight (read-only)

```sql
-- current version watermark (expect v3.1)
SELECT table_name, MAX(date_updated)
FROM etl.flat_log
WHERE table_name LIKE 'flat_moh_706_report_v%'
GROUP BY table_name;

-- result_creator must NOT exist yet
SELECT COUNT(*) AS has_result_creator
FROM information_schema.columns
WHERE table_schema = 'etl'
  AND table_name   = 'flat_moh_706_report'
  AND column_name  = 'result_creator';

-- the retrieval layer also needs these on the amrs.orders extract
-- (v1.2 reads orderer and date_created directly). If `orderer` is absent,
-- STOP: clinician_name must be adjusted first (plan D9 / Q12).
SELECT column_name
FROM information_schema.columns
WHERE table_schema = 'amrs' AND table_name = 'orders'
ORDER BY ordinal_position;

-- amrs.users must exist (officer fallback join; used by other ETLs already)
SELECT COUNT(*) FROM information_schema.tables
WHERE table_schema = 'amrs' AND table_name = 'users';
```

Baseline snapshot (compare after the build — §8 of the plan):

```sql
SELECT COUNT(*)                                        AS report_rows,
       SUM(order_id IS NULL)                           AS obs_only_rows,
       SUM(diagnostic_report_id IS NOT NULL)           AS with_fhir,
       SUM(report_date_created IS NOT NULL)            AS with_received
FROM etl.flat_moh_706_report;

SELECT COUNT(*) AS result_rows FROM etl.flat_moh_706_report_results;
SELECT COUNT(*) AS map_rows   FROM etl.concept_set_map;

-- non-panel aggregates must be identical after the upgrade
SELECT concept_id, COUNT(*) n,
       SUM(result_numeric IS NOT NULL) numeric_results,
       SUM(result_concept_id IS NOT NULL) coded_results
FROM etl.flat_moh_706_report
GROUP BY concept_id ORDER BY n DESC;
```

Operational pre-checks:

- **Disk:** the build writes `flat_moh_706_report_temp_<N>` +
  `..._results_temp_<N>` per worker — reserve ~1× the primary tables' size.
- **Memory:** each worker session sets `sort_buffer_size = 512000000`
  (~512 MB). Size parallelism accordingly.
- **Window:** between Step 2 (procedure install) and the first completed
  build, scheduled syncs for THIS table abort with
  `No watermark for flat_moh_706_report_v3.2` — by design (build-first
  guard). Other tables are unaffected. Install + build in one window.

## 1. DDL — add the column, refresh the create-script objects

`create_flat_moh_706.sql` is `CREATE TABLE IF NOT EXISTS`, so on an existing
v3.1 install it will **not** add the new column. Run the ALTER explicitly:

```sql
-- instant on MariaDB 10.3+ (appended column, ALGORITHM=INSTANT)
ALTER TABLE etl.flat_moh_706_report
  ADD COLUMN result_creator INT DEFAULT NULL;
```

Then the create scripts (no-ops on existing objects; create the queues and
refresh the `refresh_concept_set_map` definition with the wider scope and
deterministic sort_weight):

```bash
mysql <host/creds> etl < create_flat_moh_706.sql
mysql <host/creds> etl < create_flat_moh_706_results.sql   # has DELIMITER blocks: pipe, don't paste
```

## 2. Install the v3.2 procedure

The generator file is a bare `CREATE DEFINER=... PROCEDURE`. Drop the old
definition, then install (wrap in a delimiter; keep or adjust the DEFINER to
this environment's ETL user):

```bash
mysql <host/creds> etl -e "DROP PROCEDURE IF EXISTS etl.generate_flat_moh_706_v1;"
( echo "DELIMITER \$\$"; \
  sed 's/DEFINER=`[^`]*`@`[^`]*`//' generate_flat_moh_706.sql; \
  echo "\$\$"; echo "DELIMITER ;" ) | mysql <host/creds> etl
```

From this moment sync refuses (no v3.2 watermark) — expected until Step 4.

## 3. Refresh the panel map

```sql
CALL etl.refresh_concept_set_map(NULL);  -- truncates + rebuilds, wider scope
SELECT COUNT(*) FROM etl.concept_set_map; -- baseline had panels 302/1010/1019 only;
                                          -- now every set-flagged reportable concept
```

## 4. Full build (not sync)

Every build drains the queue, so populate it for the full population first:

```sql
INSERT INTO etl.flat_moh_706_report_build_queue (person_id)
SELECT person_id FROM amrs.person WHERE voided = 0;
```

Run **one worker first** and note the cycle time output (`Cycle Time (s)`,
`Est time remaining (min)`) before adding parallel workers:

```sql
CALL etl.generate_flat_moh_706_v1('build', 1, 10000, 1000);
-- parallel workers (optional, after timing worker 1): queue_number 2..N
-- with the same queue_size; every worker slices its own share of the queue.
```

Notes: worker `queue_number = 1` also runs the voided-person sweep; the
build logs the `flat_moh_706_report_v3.2` watermark on completion, which
re-enables sync:

```sql
CALL etl.generate_flat_moh_706_v1('sync', 1, 10000, 1000);  -- must complete cleanly
```

## 5. Post-build verification

```sql
-- watermark written
SELECT * FROM etl.flat_log WHERE table_name = 'flat_moh_706_report_v3.2';

-- F1 adoption: obs-only rows now carrying an adopted order
SELECT COUNT(*) FROM etl.flat_moh_706_report
WHERE report_id < 0 AND order_id IS NOT NULL;

-- F6 officer source coverage
SELECT COUNT(*), SUM(result_creator IS NOT NULL) AS with_creator
FROM etl.flat_moh_706_report;

-- F3 anti-overlap: must return 0 rows
SELECT result_obs_id, COUNT(DISTINCT report_id) n
FROM etl.flat_moh_706_report_results
WHERE result_obs_id IS NOT NULL
GROUP BY result_obs_id HAVING n > 1;
```

Then compare the §0 baseline: `report_rows` should be unchanged (F1 is
additive — same rows, now with `order_id`/FHIR/`result_creator` filled);
`with_fhir` and `with_received` should rise; per-`concept_id` counts for
**non-panel** concepts must be identical (only the `*_with_members` /
panel-member semantics may move — record those deltas).

Finally, API smoke test (the failing query shape):

```
GET /etl/lab-706/patient-list?indicators=total_urinalysis&startDate=...&endDate=...
```

asserting `clinician_name` (orderer), `testing_officer` (FHIR performer →
result creator), `date_sample_received` (FHIR → orders.date_created →
obs_datetime), `amount_charged`/`receipt_number` (encounter-level), and full
panel `results` with `Not done` placeholders. `prior_treatment`,
`condition_of_specimen`, `signature` must remain empty (D1–D3).

## 6. rest-server

If not already deployed: ship `lab-706-patient-list.json` **v1.2** +
`lab-706-aggregate.json` (`useTemplateVersion: "1.2"`) together — a mismatch
silently serves the old template.

## Rollback

- **ETL:** the table is derived. Reinstall the v3.1 generator file
  (Step 2, old file) and run a full build again (Step 4). The extra
  `result_creator` column is harmless to v3.1 (all inserts use explicit
  column lists; it stays NULL).
- **rest-server:** v1.2 requires the `result_creator` column to exist —
  keep Step 1's ALTER in place even on an ETL rollback, or revert the
  rest-server to v1.1 templates.

  service-account creators, revision chains — should be run on the analytics
  replica when reachable and attached to the plan.
